# RAG

## 定义

RAG（Retrieval-Augmented Generation，检索增强生成）是在大模型生成回答之前，先从知识库中检索相关内容作为上下文，再让模型基于这些内容生成回答的技术。它能让 AI 的答案「有据可依」，缓解幻觉和知识过时的问题。

## 核心内容

RAG 的典型流程：

```
用户问题 → 检索相关知识 → 把知识拼进提示词 → 模型基于知识生成回答 → 返回回答 + 来源
```

产品经理要理解 RAG 的价值与边界：

1. **解决什么问题**：让模型回答「私有/专业/时效性」知识，而不是只靠模型自己的记忆
2. **核心是「检索质量」**：检索到的内容如果不相关，RAG 反而会误导回答
3. **可追溯**：回答能带上「来源」，用户知道依据是什么
4. **不是万能的**：RAG 依赖知识库质量，也引入检索延迟和成本

对产品经理来说，RAG 的重点不是「怎么实现」，而是「什么时候需要它、它有哪些产品风险」。

## 常见场景

- 面试被问「RAG 能解决大模型的什么问题」
- 设计「AI 知识问答 / 企业知识库」类产品
- 判断「什么时候需要给 AI 接知识库」

## 产品经理关注点

- RAG 的价值是「准确性 + 可追溯性」，不是「技术炫技」
- 知识库质量是上限：垃圾进垃圾出，要先有高质量知识
- 检索不准会「误导」回答，产品上要设计「来源引用」让用户可判断
- 关注「时效性」：RAG 适合知识频繁更新的场景（如产品文档、政策）

## 参考答案

### 问题 1

它主要解决三个问题：一是「幻觉」，让回答有真实的知识做依据而不是凭空编；二是「私有知识」，模型没学过的公司/产品知识也能答；三是「时效性」，知识库更新了回答就能跟上。本质是「把模型的能力和外部知识结合起来」，让回答更准、更有依据。

### 问题 2

最大的局限是「检索质量决定上限」：如果知识库里没有、或检索出的内容不相关，RAG 反而会引导模型答错。另外它依赖知识库的维护质量，还引入了检索延迟和成本。所以 RAG 不是「接上就好」，需要持续优化知识库和检索，产品上还要用「来源引用」来兜底，让用户能判断回答可不可信。
