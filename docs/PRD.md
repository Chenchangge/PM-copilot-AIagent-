## 1. 产品概述

### 1.1 产品定位

PM Copilot 是一款面向产品经理求职者的 **AI 学习与模拟面试助手**，主要服务大学生、应届生与初级产品经理。

### 1.2 核心问题

产品经理学习过程中存在以下断层：

```
看过知识 → 理解知识 → 实际应用 → 面试表达
```

用户普遍「看懂了」知识，却难以在面试中「讲清楚」，知识与表达之间缺乏反馈闭环。

### 1.3 核心价值

PM Copilot 不是单纯提供 AI 问答，而是帮助用户把「知识学习」转化为「面试表达能力」。

通过：

```
学习 → 模拟面试 → AI 评价 → 发现薄弱点 → 推荐学习 → 再次面试
```

形成完整反馈闭环。

### 1.4 产品闭环

```
        ┌─────────────────────────────────────┐
        │                                     │
        ▼                                     │
   ┌─────────┐   ┌──────────┐   ┌──────────┐ │
   │  学习    │──▶│ 模拟面试  │──▶│  AI 评价  │ │
   └─────────┘   └──────────┘   └────┬─────┘ │
        ▲                              │       │
        │                      ┌───────▼──────┐│
        └──────────────────────│  发现薄弱点   ││
                               └───────┬──────┘│
                                       │        │
                               ┌───────▼──────┐ │
                               │  推荐学习     │─┘
                               └──────────────┘
```

## 3. 产品目标

### 3.1 MVP 阶段目标

1. 帮助用户系统学习产品经理知识
2. 帮助用户通过 AI 问答理解知识
3. 帮助用户制定基础学习计划
4. 提供产品经理模拟面试
5. 根据面试回答进行结构化评价
6. 识别用户薄弱知识点
7. 推荐对应知识进行学习

### 3.2 最终目标

形成「学习 → 实践 → 反馈 → 再学习」的持续闭环，让用户在真实面试前完成充分、有针对性的准备。

## 4. 产品范围

### 4.1 MVP 范围

#### 学习

- 产品知识库

- 学习计划

#### 模拟面试

- 面试方向选择

- 多轮面试
- AI 动态追问
- 面试报告
- 能力维度评价
- 薄弱点分析
- 知识推荐

#### 个人中心

- 学习记录
- 面试记录
- 基础设置

### 4.2 明确排除范围（MVP 不包含）

登录注册 · 社交 · 社区 · JD 分析 · 简历优化 · 简历生成 · PRD 自动生成 · 求职推荐 · 招聘企业端 · 付费系统 · 会员 · 排行榜 · 积分 · 游戏化系统

> 以上功能**一律不在 MVP 范围内**，不得擅自扩展。

### 4.3 用户身份方案【MVP】

MVP 不加入登录/注册，采用**匿名本地身份**：

- 首次使用时生成匿名 `user_id`
- 使用 `localStorage` 保存
- 学习记录、面试记录等数据与该匿名 `user_id` 关联
- 后续若增加账号系统，再考虑匿名数据迁移

> 当前不实现完整登录系统。

### 4.4 核心产品原则：BYOK（Bring Your Own Key）【MVP】

PM Copilot 采用 **BYOK** 模式：

- 平台不统一提供模型额度
- 用户自行填写并配置自己的模型 API Key
- 用户自行承担对应模型 API 调用费用
- API Key 不允许写入前端代码
- API Key 不允许提交到 GitHub
- `.env`、密钥、真实 API Key 必须加入 `.gitignore`
- 后端负责模型 API 调用

> 平台只提供「学习 / 面试 / 评价」等产品能力，模型推理由用户配置的 API 承担，成本与权限归用户所有。

## 7. 功能需求

### 7.1 知识库【MVP】

**知识分类：**

产品基础 · 产品设计 · 数据分析 · AI 产品 · 工具 · 产品经理面试

**知识内容结构：**

| 字段（字段名） | 说明 |
| --- | --- |
| 定义（definition） | 该知识点的核心概念 |
| 核心内容（coreContent） | 关键要点 |
| 常见场景（commonScenarios） | 实际应用场景 |
| PM 关注点（pmFocus） | 对 PM 工作的具体意义 |
| 常见面试问题（interviewQuestions） | 对应高频面试题 |
| 参考回答（referenceAnswers） | 回答思路与要点 |

**知识库第一阶段规模：** 30～50 个高质量知识点，内容需原创、贴合真实面试，不简单复制互联网文章。

### 7.2 AI 知识问答【MVP】

用户输入产品经理相关问题，AI 基于知识库给出回答。

**未来流程（产品需求）：**

```
用户问题 → 知识检索 → Top-K 召回 → Prompt 组装 → 生成回答 → 返回来源知识
```

**页面展示：**

- AI 回答
- 参考知识
- 来源

> 【技术】知识检索依赖 Embedding + 向量检索，属技术实现手段，见 [9. RAG 产品需求](#9-rag-产品需求)。当前阶段仅为产品需求描述，未实现。

### 7.3 学习计划【MVP】

MVP 仅提供单一固定学习计划：「AI 产品经理 14 天学习计划」。

**不实现：**

- 用户自主选择多个学习目标
- AI 个性化生成计划
- 动态调整学习计划

> MVP 的目标是先验证「学习计划 → 学习 → 面试」闭环，而不是验证复杂的个性化规划能力。

**学习计划包含：**

- 每日主题
- 学习知识
- AI 问答
- 面试练习
- 完成状态

### 7.4 模拟面试（配置）【MVP】

用户可配置：

| 配置项 | 选项 |
| --- | --- |
| 方向 | C 端产品经理 · B 端产品经理 · AI 产品经理 · 数据产品经理 |
| 难度 | 基础 · 中等 · 困难 |
| 类型 | 产品基础 · 产品设计 · 需求分析 · AI 产品 · 综合面试 |

### 7.5 AI 模拟面试（动态追问）【MVP】

**未来流程（产品需求）：**

```
AI 提出主问题 → 用户回答 → AI 分析回答 → AI 动态追问
     → 用户继续回答 → 多轮交互 → 面试结束
```

**关键要求：** 不是随机题库，需根据用户上一轮回答生成有针对性的追问。

### 7.6 AI 面试评价【MVP】

**评价方法：** Rubric + 参考答案/核心关键点 + LLM 结构化评价。

**能力维度与权重（最终）：**

| 维度 | 权重 |
| --- | --- |
| 产品思维 | 30% |
| 需求分析 | 20% |
| 逻辑与表达 | 20% |
| AI 知识 | 15% |
| 业务意识 | 15% |

> 权重合计 100%。「表达能力」不再作为独立维度，已纳入「逻辑与表达」。
>
> AI 评价阶段由模型输出 **5 个维度的结构化评分、评价依据、优势与问题**；最终总分由**后端按照上述固定权重计算**，不由 LLM 直接决定最终总分。
>
> 当前仅为产品设计，暂未实现真实 AI 评价。

**最终报告包含：**

- 综合表现（总分）
- 各能力维度得分
- 优势
- 薄弱点
- 推荐学习

### 7.7 薄弱点 → 知识映射【MVP】

建立「能力维度 → 知识点」的映射关系。

**示例：**

```
AI 知识不足 → RAG / Embedding / AI 评测 / AI 产品指标
```

**闭环示例：**

```
面试回答 → AI 评价 → 薄弱点：RAG → 知识库 RAG → 推荐学习 → 知识详情
```

这是产品核心闭环之一。

### 7.8 AI 模型 / API 设置【MVP】

「我的」下的设置入口，让用户管理自己使用的 AI 模型，并了解不同模型支持的能力。

**支持配置的模型（示例）：**

- DeepSeek
- OpenAI
- Claude
- Gemini
- 其他兼容 OpenAI API 的模型

**每个模型至少包含字段：**

| 字段 | 说明 |
| --- | --- |
| 模型名称 | 展示用名称 |
| API Key | 用户自己的密钥，脱敏显示 |
| API Base URL | 可选，自定义端点 |
| Model 名称 | 实际调用的 model 标识 |
| 是否已配置 | 配置状态 |
| 测试连接 | 连通性校验 |

> 本阶段仅定义产品需求，不实现具体厂商 SDK；各厂商通过统一接口抽象接入。模型配置与登录/账号体系解耦（MVP 无登录，配置属于本地个人设置）。

页面详细交互与 UI 设计见 [docs/ai-models-page-design.md](./ai-models-page-design.md)。

## 8. AI 能力与模型设计【MVP】

### 8.1 AI 能力抽象

不与具体模型/厂商强绑定，将 AI 能力抽象为：

| 能力 | 说明 |
| --- | --- |
| 文本生成 | 生成自然语言文本 |
| 推理 | 逻辑推理、分析与决策 |
| 结构化输出 | 按 schema 输出 JSON 等结构化结果 |
| 多模态理解 | 理解图像等非文本输入 |
| 图像生成 | 生成图像 |
| Embedding | 文本向量化，用于检索 |

### 8.2 功能 → 能力需求映射

不同产品功能声明自己所需的能力：

| 功能 | 所需 AI 能力 |
| --- | --- |
| AI 知识问答 | 文本生成 + RAG（Embedding） |
| 模拟面试（提问 / 动态追问 / 回答分析） | 文本生成 + 推理 + 结构化输出 |
| 面试评价（评分 / 薄弱点分析） | 推理 + 结构化输出 |
| 知识库 Embedding | Embedding |
| 产品设计辅助（规划） | 依具体能力而定（文本结构化 / 多模态 / 图像生成） |

### 8.3 AI 能力使用原则

统一采用「**功能需求 → AI 能力需求 → 模型能力匹配**」，而非「**功能 → 固定模型**」。

- ❌ 错误：知识问答固定使用 DeepSeek
- ✅ 正确：知识问答需要「文本生成 + Embedding」，由用户已配置且支持这些能力的模型承担

「思维导图」本身不一定需要图像模型：可由 LLM 输出结构化节点、前端渲染；只有真正需要多模态 / 图像生成的功能，才明确声明对应能力要求。

### 8.4 模型路由原则

```
用户配置模型
↓
系统识别功能所需能力
↓
筛选支持该能力的模型
↓
调用对应模型
```

若用户未配置满足要求的模型，给出明确提示，例如：

> 「当前功能需要支持多模态的模型，请先配置支持该能力的模型。」

### 8.5 模型管理 MVP 边界

**MVP 只做：**

- AI 模型 / API 设置入口
- 用户配置自己的 API
- API 连通性测试
- 模型能力标签
- AI 功能与模型能力之间的匹配规则
- 没有合适模型时给出提示

**MVP 暂不做：**

- 自动寻找模型
- 自动购买 API
- 平台统一 API Key
- 自动充值
- 模型价格比较
- 模型排行榜
- 模型性能排行榜
- 按价格动态切换模型
- 多模型同时生成答案并投票
- 复杂 Agent 模型编排

## 9. RAG 产品需求【MVP · 技术】

RAG 属于**技术实现手段**，产品层面的目标是：**提高知识问答的准确性和可追溯性**。

**未来技术方案（规划，非当前实现）：**

```
Markdown → 文本切分 → Embedding → Chroma / FAISS
     → Top-K 检索 → Prompt → LLM（用户配置） → 回答 + 来源
```

> 其中「Embedding」对应 [8.1](#81-ai-能力抽象) 的 Embedding 能力，「生成回答」对应文本生成能力，均由用户已配置的模型承担（见 [8.4](#84-模型路由原则)）。技术选型在后续技术实现阶段进一步确定，当前不实现。

### 12.3 安全与 API Key

**产品原则（BYOK）：**

- 用户自行填写并持有 API Key，平台不统一提供额度
- API Key 不暴露给前端代码
- 前端不直接暴露第三方 API Key
- 后端负责调用模型 API

**技术实现（与产品原则分离）：**

- Key 不得硬编码在前端
- Key 不得提交 GitHub；`.env`、密钥、真实 API Key 加入 `.gitignore`
- 生产环境使用环境变量或安全存储
- 日志不得输出完整 API Key
- UI 中 Key 默认脱敏显示

## 13. 风险与限制

| 风险 | 说明 |
| --- | --- |
| LLM 幻觉 | 回答可能不准确，需引用来源 + 兜底 |
| AI 评分稳定性 | **重点研究问题**（见下） |
| AI 追问质量 | 追问可能偏离或浅层 |
| RAG 召回质量 | 检索不准会误导回答 |
| 知识库质量 | 内容原创性与覆盖度影响上限 |
| API 响应延迟 | 影响面试实时体验 |
| API 调用成本 | 影响产品可持续性 |
| 用户测试样本较少 | 5～10 人结论代表性有限 |

### 13.1 重点研究问题：AI 评分稳定性

通过重复测试同一回答，研究以下方案对评分稳定性的影响：

```
自由评分 → Rubric → 参考答案关键点 → 结构化输出
```

目标是找到可复现、可解释、稳定的评分方式。
